# Owner-Controlled Agent Rules

Owner delegation is optional. A normal database integration still starts with
`runner start --from-env DATABASE_URL --cli`; it does not require this setup,
a separate control database, or a new identity provider.

Use delegation when authorized customers or account administrators should be
able to customize what their agents may do. The application operator reviews
the supported operations and hard safeguards. Owners can edit only the
explicitly delegated part. Their agents cannot activate their own policies.

## Local Operator Setup

The local prototype uses the project's configured SQLite control store or
PostgreSQL `runtime_store`, not an audit mirror. Existing file-backed projects
need one explicit migration:

The commands below use `synapsor.actions.runner.json`, the runtime file
generated by model-guided Read/Action setup. For a manually named unified
runtime file, substitute that reviewed file consistently in every command;
do not substitute the separate Read launch file.

```bash
runner policy storage --config ./synapsor.actions.runner.json --project-root .
```

Runner previews the existing active and disabled authority, destination and
exact configuration before asking for confirmation. It preserves reviewed
Read/Action digests, selected boundaries, disabled drafts and execution
settings. Changed artifacts invalidate the preview. An interrupted committed
migration resumes from its frozen receipt. After cutover, files are exports
and recovery inputs, not a second writable source of active authority.

Parent delegation is a separate operator decision:

```bash
runner policy delegation --config ./synapsor.actions.runner.json \
  --name customer_agent_rules
```

This opens the same model-guided conversation used for Boundary authoring.
For a new parent, identify the personal or shared-account owner, authorized
human sign-in subject and agent workload from your trusted backend. These
bindings are collected locally and cannot be changed by the drafting model.
For an existing parent, the saved bindings are retained without asking again.
Describe the customizable conditions and mandatory restrictions in ordinary
language; inspect exact details or ask follow-up questions before the separate
operator confirmation. Selecting this optional setup does not enable it.

The client handoff also offers this path under **More options**. It is not a
required step for ordinary database onboarding. Exact manual configuration
remains available with `--input ./owner-delegation.json`.

The document uses `synapsor.policy-management-parent.v1`. Its sections are:

| Section | Operator Decision |
| --- | --- |
| `managers` | Authenticated subjects, personal/shared scopes, inspect/draft/activate/revoke rights |
| `delegation` | Agent names, existing compiled outcomes, verified fact vocabulary, operators and hard limits |
| `agent_owners` | Which owner or shared account may manage each agent |
| `runtime_delegations` | Acting agent, delegator, owner and mandatory policy layers for each workload |

The exact document is available in the review; inspect it before enabling
delegation. Runner checks vocabulary against the current compiled Action
rules, not column-name guesses. Unknown facts, unsupported effects and stale
Action digests are rejected. Replacing the parent requires affected child
policies to be revalidated. Spent and reserved allowance is not reset.

This command is a trusted local deployment-operator surface. Someone who can
replace the Runner process or modify its control store is outside Runner's
service-level enforcement boundary. Do not give untrusted tenants filesystem
access to this process or distribute the SQLite file to owners.

## Configure Owner Chat

Prepare a separate `owner-connection.json` containing environment-variable
names and your backend's issuer/audiences, not credential or signing-key values:

```json
{
  "owner_management": {
    "parent_name": "customer_agent_rules",
    "policy_name": "my_agent_rules",
    "scope": "personal",
    "credential_env": "OWNER_ASSISTANT_TOKEN",
    "authentication": {
      "provider": "jwt_asymmetric",
      "issuer": "https://identity.example",
      "audience": "runner-owner-assistant",
      "public_key_env": "OWNER_IDENTITY_PUBLIC_KEY"
    },
    "human_review": {
      "credential_env": "OWNER_HUMAN_REVIEW_TOKEN",
      "audience": "runner-owner-human-review"
    }
  }
}
```

Review and install only these sign-in settings through the operator command:

```bash
runner policy connection --config ./synapsor.actions.runner.json \
  --input ./owner-connection.json
```

Do not manually merge authentication into an execution-bound runtime file.
Runner shows the exact sign-ins and preserves unrelated source, execution,
Read/Action and owner policy settings. Existing enabled execution requires a
second explicit confirmation to bind the same execution policy to the changed
sign-ins. Neither confirmation performs a source write or activates an owner
draft. Declining either decision leaves both config and authority unchanged.

If sign-ins were already added after migration and startup reports
`POLICY_EXECUTION_BINDING_CHANGED`, run the same command without `--input`.
Recovery accepts only a provable prior binding: for initial setup, removing
the newly added owner blocks must reproduce the exact stored binding digest.
For later hand-edited sign-in changes, supply `--previous-config` with the
previously reviewed runtime config (relative paths retain their original
runtime-config directory). Other source, context or storage edits are refused.
Never repair this by editing ledger hashes. Exact details and decline remain
available even when normal runtime startup is blocked.

`scope: "tenant"` selects a shared-account
policy only when the current authenticated grant permits it. A config entry
alone grants no management rights.

The trusted backend issues short-lived signed credentials with subject,
tenant, principal, actor kind, session and policy channel. Human review and
assistant access use separate audiences and credentials; never give the
human-review token or signing key to the model. Runtime agents use the
separate `action_rules.owner_delegation` workload credential and reviewed
agent/delegator association. Caller-supplied tenant/principal text is not
authentication.

The owner-authentication protocol supports RS256 and ES256 for
`jwt_asymmetric`, verified only with the configured public key. It never
selects an allowed algorithm from a token's request; HMAC signatures cannot
use that public key. The owner configuration does not have an `algorithms`
field. The general HTTP session verifier's separately configured algorithm
allowlist remains mandatory and unchanged. Symmetric owner configurations
use only HS256 with their dedicated backend-held secret.

Start local Ask or the existing stdio MCP integration. Owner management is
currently a local Ask/stdio prototype. HTTP serving explicitly refuses this
configuration rather than silently exposing a different authority surface.

An authorized operator or account administrator can select an owner before
starting the same model-assisted chat:

```bash
runner policy chat --config ./synapsor.actions.runner.json
```

The picker lists only explicitly authorized scopes, with bounded search and
paging. A sole authorized owner opens directly. Identically named people in
different accounts remain distinct. Inspection-only grants are labeled;
they cannot save or activate edits. Revoked grants take effect on subsequent
calls, including a pending confirmation.

Each selection starts a fresh settings-only conversation. It neither carries
another owner's chat history nor opens their source records. Selecting an
owner changes the management context, not the authenticated data identity.
Only the selected scope is disclosed to the provider after the normal model
permission review. Changing rules still uses the same four tools and the
separate exact human confirmation described below.

## Edit From The Same Client

The tool names stay fixed:

| Tool | Authorized Settings Operation |
| --- | --- |
| `app.describe_data` | Discover the selected owner's settings and delegable vocabulary |
| `app.explore_data` | Read current settings and issue a scoped policy reference |
| `app.describe_actions` | Describe the permitted policy-revision request |
| `app.request_change` | Validate and save a disabled revision |

Settings requests use `policy_view: "agent_rules"`. They are explicitly
separate from source-row reads and changes. A settings-only session does not
claim Read authority is active. Discovery is scoped and paginated; inaccessible
owners are not a searchable source catalog.

Ask, for example: "For my replenishment agent, require my review above 20
units and allow only routine requests." The assistant receives only the
authorized policy and verified vocabulary. Runner validates typed conditions,
parent bounds and affected agents, then returns a disabled draft and a review
continuation. Unsupported requirements remain unresolved, not approximated.

In local Ask, `/review-rules` opens the deterministic before/after review.
Inspect full details or leave the draft disabled. Activation requires the
separate human-review credential and an explicit decision bound to the exact
revision. A plain model message saying "yes" cannot activate it. Generic MCP
clients can propose the same edit and reach this trusted continuation; their
ordinary tool-execution confirmation is not owner-policy authorization.

## Enforcement And Receipts

Each request and queued execution rechecks current parent and required owner
policies. Revocation blocks new dispatch. An execution already dispatched may
finish under the authority admitted at dispatch, even if the rule changes before
the source transaction commits. The source transaction still rechecks its exact
facts and effect. Missing or stale policy layers fail closed before admission.
Replacing rules neither rewrites an earlier approval nor undoes completed data.
Inspect receipts before retrying uncertain work; a new request needs a fresh
decision under current rules. Replacement review reports a bounded queue snapshot
and labels incomplete or unavailable counts explicitly.

`runner worker status` identifies unstarted requests blocked by changed rules.
Cancellation requires the operator authority recorded when the request was
queued; a newer policy cannot remove an earlier required cancellation role.
For older queue entries without that record, production cancellation needs the
original reviewed worker configuration and its exact policy digest. If that
trusted history is unavailable, Runner refuses cancellation rather than guessing
the old permissions. Do not edit queue records or reset approvals to retry work.
Cancellation applies only before a worker lease, not to already dispatched or
uncertain execution. Completed changes still require a separate reviewed change
to reverse their business effect.

Hard shared allowances measure their declared successful effects plus
outstanding reservations, not merely approvals. Two agents cannot allocate
the same allowance. A new revision, agent or session does not reset it.
Unknown outcomes keep capacity reserved until reconciled against a receipt.
Human approval cannot override an independent hard cap.

The supported local execution path is guarded same-database writeback with
current scope, freshness, version and exact-effect checks. Approval is not
execution. Only a successful durable source receipt establishes completion;
this feature is not an external payments service or a cross-system transaction.

For PostgreSQL RLS sources, the execution identity comes from the approved
proposal's recorded trusted context. A physical principal column is not
required when the reviewed database policy enforces that scope. Runner binds
the same scope to the source transaction and the immutable delegation proof;
missing or inconsistent context is refused. Changing the worker's environment
or broadening database grants is not a recovery for a scope or proof refusal.

Read/Action/execution authority, owner management, authenticated workload
binding and worker readiness are separate prerequisites. Enabling owner
management alone does not grant source reads, approve operational requests,
start a worker, or execute a source change.
