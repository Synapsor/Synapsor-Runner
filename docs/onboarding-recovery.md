# Guided Setup Recovery

Setup retains the reviewed job, business-source snapshots and disabled drafts.
Read, Action and execution authorization remain separate recorded decisions.

## Protocol Readiness Is Not Data Authority

A local stdio client can initialize and list the four fixed tools before a
runtime customer identity is supplied. This check does not read source rows,
list a customer's catalog, request a change or run a worker. Every actual Read
or Action call must resolve trusted scope before routing, lookup or errors that
could disclose catalog information. Production HTTP authentication is unchanged.

Client configuration, a successful temporary handshake, a running client and a
running execution worker are different states. Setup reports them separately.
Approved or queued requests are not completed requests: completion requires the
guarded execution result and its durable receipt.

## Unchanged Resume

After client setup, `start --cli` offers **Edit rules with model** and
**Manual Boundary editor** alongside client use. Rule editing returns directly
to metadata-only authoring; it does not require a runtime customer identity,
start terminal Ask, reinstall client settings, or interrupt a connected client.
The model can add another reviewed behavior to the existing action catalog.
Read, Action and execution changes still require their own exact review.

The saved job is bound to its generation lock, schema, database-role posture and
provider. Client continuation additionally binds the exact active Read and
Action digests. An unchanged resume does not regenerate timestamps, reactivate
identical authority or repeat previously assigned client responsibilities.
It also retains already-reviewed private verification fields; reconstructing a
saved draft is not a request to minimize that draft again. Intentional edits
still validate and review their new revision.

Once Read and Action are active, paused execution setup returns to client setup
with an **Execution setup** option. That option reviews the active revision's
writer and execution policy directly; it does not redraft the job or start a
worker. Connecting a proposal-only client remains possible, with execution
reported as off. Semantic outcome names use the same qualified-name grammar in
Action compilation and execution configuration, including three-part names.

Application responsibilities are restricted to reviewed customer-selection and
status-presentation contracts. Assigning those responsibilities does not claim
the client implementation was tested. It cannot waive eligibility, privacy,
scope, approval, execution or other mandatory database checks.
When one policy passage contains both a Runner guarantee and an application
duty, rechecking matches the exact duty instead of mistaking the first passage
entry for its assignment. Changed source, authority or duty still requires a
new assignment.

## Business Clarification And Planning Failures

A question about the meaning of a field is not automatically a request to
change access. The model can return an `already_satisfied` reconciliation with
exact field states. Runner checks those states against the current catalog,
records source-bound interpretation evidence and rechecks policy coverage.
The Read digest, Action rules and activation state remain unchanged. A partial
match still needs the remaining exact changes; an empty assertion of success
does not bypass validation. Ambiguous timestamps are not classified as private
solely from their names.
An answer that both confirms one field and changes another retains the confirmed
meaning only after those field states are checked against the resulting revision.
The field-exposure tool schema permits operation settings only on Runner-only
decisions, matching the validator; bounded correction identifies the exact field
and incompatible property instead of returning a generic combination error.

An established privacy mismatch uses the bounded Read-revision operation in the
same conversation. It does not ask the operator to translate a diagnostic into
another instruction or mistake an Action dependency link for an approval edit.
Coverage is checked again after the revision; a failed repair leaves activation
blocked and permits an explicit retry. Runner-generated repair instructions are
not recorded as new operator policy decisions.
Retained clarification turns keep the model's question and the operator's
answer in their original roles after resume and retry. Ordinary conversation
turns remain unchanged; a generated repair is never relabeled as a user request.

Already supplied explanations of coded fields are retained as quoted operator
evidence. Unknown or ambiguously named fields still require clarification;
the model cannot invent a quote or use a hidden field as naming evidence.
Before review, missing labels can be repaired without changing field access,
operations, exclusions or business rules. Every dependent Action is compiled
against the proposed Read revision before it is saved. Metadata-only generation
changes can be rebound from the exact saved snapshots; schema, role or trusted
context changes cannot. All affected outcomes are prepared before replacing
the disabled Action bundle, so a later outcome cannot leave a mixed dependency.

Automatic-approval limits explicitly shared across actions remain shared in
each applicable policy. Decomposing a job must not create a fresh allowance
per action. A saved mismatch can reopen just the approval limits while
preserving eligibility, effects, reviewer, execution intent and outcome names.
The operator still reviews the changed revision. A later explicit correction
can replace the original shared-limit instruction; asking a question about it
does not change that instruction.

Incomplete structured submissions are the model's responsibility, not a request
for the operator to supply JSON components. Runner gives a bounded internal
correction and, if the model still cannot finish, retains the draft with a
specific failure and retry/model-selection path. This does not guarantee that
every local model can complete a supported business task.

The conversation asks one short business question without repeating the saved
action policy. Exact reasoning remains in `/details`. An unavailable explanation
does not discard the question or disable deterministic inspection.
When attached-policy review owns the next question, a completed Action tool
exchange does not also print a second recap. Its result remains in the local
review and conversation context. Actual unanswered business questions still
stream normally.

An explicit request for automatic completion prepares the supported disabled
execution configuration before policy coverage. It is not another business
decision and does not enable a writer or worker. Separate execution review,
writer validation and operator authorization remain required. A proposal-only
request does not receive this configuration.
Exclusions of unrelated effects, such as allowing plan changes but forbidding
refunds, do not cancel that execution request. Explicit global no-write or
proposal-only instructions still prevent execution preparation.

Missing authenticated-session wiring is a separate deployment prerequisite only
when the candidate already has reviewed customer scope. It stays unverified
through authority review and appears again at client setup. Local fixed-identity
testing is not production authentication verification. Undecided row scope,
privacy or eligibility cannot be moved into this prerequisite to unblock review.

Job routing uses a single bounded correction: at most two provider requests
with the same approved source and context. The typed Read routing summary may
be a noun phrase; it need not repeat a particular verb. An individual word in
a business request does not establish a multiword table identity. The later
metadata-aware mapping, policy coverage and exact review still determine the
actual permitted resources and operations.

Operator-only planning diagnostics are saved under
`.synapsor/boundary-authoring/diagnostics/planning-*.json` with private file
permissions and a maximum of 16 records. They retain initial/correction
categories, precise validation reasons, provider stop status and bounded
structural response metadata. They do not retain raw arguments, provider
messages, credentials or endpoint URLs. A manual retry gets a separate record
instead of erasing the failure. Older failures without these records cannot be
retroactively assigned a cause.

A deterministic starting draft is not represented as equivalent to model
interpretation of an attachment. The full source and unresolved requirements
remain available and must be checked before activation.

## Changed Database

An explicit rescan reconciles saved field decisions against current metadata.
It does not activate new authority. A saved job on the same Boundary can be
revalidated without asking the operator to restate the job or reattach files.
Old analyses, partial model checkpoints and client activation checkpoints are
discarded; current structural disclosure requires fresh permission. Business
history is context, not evidence that the new structure passed validation.

Retaining the same business rules must still review the changed Read revision
and rebuild dependent Actions against current structural facts. Missing private
resources or unsupported relationships remain blockers, not implicit grants.
Existing authority is not overwritten merely because a revalidation started.
An invalid resume digest or a different selected Boundary is not rebased.

Read mapping can ask up to four distinct business clarification questions,
retaining every answer through mapping and correction. Identical answered
clarification requests are refused rather than shown again. The bounded follow-up budget
does not authorize database-value disclosure: that still has its own exact
preview and one separate consent. Exhaustion preserves the saved conversation
and returns a concrete diagnostic, not a fabricated draft.

New metadata inspection distinguishes boolean contact preferences, such as
`email_opt_in BOOLEAN`, from fields that contain contact addresses. Independent
secret, medical and write-only flags remain protected. This improves disabled
draft preparation; it does not remove an operator's existing saved exclusion.

## Supported Insert Workflows

Current Action Rules require a reviewed, scoped subject reference, including for
INSERT proposals. An operator can choose a supported workflow anchored to a
selected existing record. A subject-free insert is not currently supported and
must remain a concrete blocker when that is a business requirement. Runner must
not invent a relationship or add a selected-record requirement without the
operator's agreement. Approval, human fallback and refusal remain branches of
the same action; a clarification must not create a duplicate outcome.

## PostgreSQL Private Verification

Action runtime configuration carries the RLS setting names from its exact
reviewed Read dependencies. It does not copy concrete tenant/principal values.
Missing wiring can be restored from that exact authority during client setup;
conflicting setting names or stale dependencies are refused.

Private verification may use locking reads. PostgreSQL can permit a scoped
SELECT while excluding the same row from SELECT FOR UPDATE when an applicable
UPDATE RLS policy is missing. Writer preflight checks this prerequisite as well
as exact column grants. It does not create policies, bypass RLS, or claim that
the existence of a policy proves a particular row is eligible. Source predicates
and expected-version guards are still checked in the execution transaction.

See [PostgreSQL Writer Column Grants](postgres-writer-column-grants.md).
