## Pure comparator design (not yet implemented)

The producer consumes a **current resolved projection** from the existing attributed requirement owner. It does not receive raw prose to parse. A bounded requirement union covers:

1. Reviewer role/quorum and approval posture for the exact selected outcome.
2. A complete existing normalized approval-limit tuple: identity, kind, trusted scope, maximum, window, selector/capability and all other meaningful existing fields. Pair the tuple to its exact intended limit/Action; finding its numbers in unrelated limits is not satisfaction.
3. Disabled execution posture for the exact effect (`proposal_only` or `supervised`). This is a configuration requirement, not a write or activation permission.
4. Explicit unresolved/unsupported/conflicting interpretation. Such a requirement cannot become “none” merely because a subsequent model reply omitted it.

Each projection carries exact meaning identity, applicable current Source/operator support reference and dependency binding as distinct concepts, resolved by its owner. The comparator checks currentness and structural equality against the **whole compiled candidate**; it returns per-requirement satisfied/missing/conflicting/stale/unsupported evidence, never approval or a persistence operation. An empty requirement array is meaningful only when the owner has established the current interpretation's completeness; omission is pending.

Typed replacement must be linked to its exact predecessor and explicit confirmed replacement event. A later raw sentence or matching display value cannot supersede an earlier applicable decision. Normalization can use existing compiler semantics (for example selector representation) but cannot collapse differing targets or infer an unmentioned condition. After each model/human wait the owner re-resolves coherent current records; no retained unchecked snapshot.

Required small test matrix before retiring active parsers: exact tuple match; crossed maxima/windows; equal value in another scope; joint vs per-outcome selector; tenant vs person; unknown interpretation; omitted previously established requirement; unrelated edit; explicit replacement of one limit retaining others; Source/answer/context drift; wrong outcome; changed execution posture without applicable decision; applicable proposal-only with unrelated operation exclusions; full candidate still disabled and default-No. Successful prepared model responses see only actual current inputs and declared operator facts.
