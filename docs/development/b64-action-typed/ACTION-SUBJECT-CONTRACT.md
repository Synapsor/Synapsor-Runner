# Proposed finite Action subject requirement binding

Status: design for independent review; **not an accepted format or implemented authority**. Main owns public wiring and shared structural scope review. This fits B64's existing window and introduces no extra lane, model allowance or database capability.

## Current seam and missing fact

`preparePhaseResources` lists Verification `source.kind = subject_ref` resources and every Effect/atomic Effect target. That is an exact target inventory, not a statement that a business operation is limited to the signed-in person. Catalog `principal_scope` describes technical configuration. Neither one can replace the deleted English `jobRequestsPrincipalIsolation` decision.

For an Action's current public subject, resolve the exact applicable confirmed Read subject binding and retain its meaning and dependencies. That establishes how its existing subject reference was obtained; it does **not** grant new writes or disclosure. For a private/new target, use existing compiled relationship/guard evidence only for its technical properties. Missing business applicability remains pending and goes through an existing typed Action question. Never reuse a Read-disclosure question as private Action authority.

## Bounded record proposal for review

Use the existing native OperatorQuestion owner/history and existing Action checkpoint, not a second store or an `accepted` flag. An Action-specific subject proposal needs these finite fields:

- Exact Action identity: selected outcome, immutable selected baseline identity/digest when editing, and actual producer completion. A later search for the newest authority cannot resolve it.
- Applicable request/Source identity and current dependency digest, separately from proposal meaning identity and producer/commit identity.
- Per exact target (Verification subject root or Effect target), a typed choice: `trusted_principal`, `reviewed_scope` with a host-advertised exact scope reference, or `unresolved`. A target cannot be omitted, duplicated, merged by label or selected from an unrelated work item.
- Host scope references bind the current source/schema/role/configuration and reviewed structural acknowledgements. They are metadata facts, never model-supplied SQL, a raw row value or an implicit permission.
- The proposal cites the actual bound operator answer or applicable original Source interpretation. A model assertion alone cannot be confirmed as if the operator supplied it.

The narrow durable format decision is still required: add an Action subject binding/value to the existing strict question union and a reference to that question in the current Action checkpoint. Do **not** hide a typed value in `attributed_meaning` text, broaden `read_scope`, or add a competing question/accepted flag. Existing B64 checkpoint handling for a missing field must be decided explicitly (safe pending when no completed Action consumer exists; never an old record silently interpreted as a scope decision). No codec edits until Main and the independent reviewer agree.

## Transition and save ownership

1. Runner publishes bounded current target/options/context to the model. The model submits a typed unresolved item or proposed interpretation; raw narration is inert.
2. Existing question host records the actual completed producer handoff before waiting. Natural operator words are captured verbatim. The model maps them only through the same question/context identity; unknown remains pending.
3. Runner renders the exact business scope and its technical details. Group confirmation is default-No and binds the full proposal and current dependency view. Direct choices use the shared typed-input presenter with host-advertised options; they cannot introduce an option.
4. Existing protected Resume save acknowledges the question revision. The Action producer may consume only that acknowledged reference. Recheck coherent current dependencies after every human/model wait and under the save owner; no lease across waiting and no arbitrary latest-state adoption.
5. Compilation still enforces every guard, Source applicability and scope path. Source disabled save, activation, execution consent and worker grants remain separate. A scope answer grants none of them.
6. Replace preserves the previous raw words/proposal/No in history and creates the next exact question revision under existing budgets. Cancel, relevant drift, concurrent save and interrupted acknowledgement retain existing fences. They cannot resurrect an older Yes or replay a completed response.

## Independent counterexamples requested

Actual production handlers/native saves: an Action new private root absent from Read; a public root with current versus stale Read subject binding; tenant-only scope presented as person scope; duplicate business labels with distinct targets; model omission of one atomic target; answer mapped to another outcome; relevant role/configuration drift after readback; unrelated presentation edit retaining applicability; Replace/cancel and cold Resume; unknown answer; failed or uncertain protected save. No fixture-specific logic or private oracle data in prepared responders. A component pass is not public Resume-CAS acceptance.

## Adjacent constraint migration

Active approval-count/scope/duration and execution-mode English guards currently protect real omissions. Their replacements need the same separation: typed proposed constraints attributed to exact Source/operator records, independently confirmed applicability, then structural comparison with the complete compiled draft. Existing Source counting and execution review owners should supply those projections. Removing the parsers without that binding would silently drop safety checks; leaving them behind is not B64 completion. These rows remain open and separate from the accepted typed-result dispatcher.

## Exact adjacent record limits (code inspection)

`PolicyPassage.evidence_checks` already carries typed path/equality claims against a Source range, but a model-submitted matching value is not proof of semantic applicability. `counter_requirements` and `CountingDecision` cover the counted outcome set (`required_capability`), not the amount, window, reviewer quorum or execution posture. `CountingRequirementBinding` still comes from English clause association and is therefore not an acceptable typed source of those requirements. `receipt_requirement` and `writer_maintenance` are deliberately narrow unrelated decisions. Do not reuse any of those records as a blanket Action intent cache.

For approval/execution removal, the minimum reviewed extension is a bounded attributed Action requirement interpretation using the existing question/Source owners: exact Source/operator support, selected outcome, typed value (finite reviewer count/role, limit tuple, or execution posture), current dependency identity and unconfirmed/confirmed history from the existing question. Only the matched current interpretation can be compared to the whole compiled candidate. Unsupported counting windows and ambiguous or conflicting requirements remain pending. Replacement must invalidate the exact old interpretation rather than append an overriding sentence. Until that extension is approved and tested, the old active constraint calls are an open migration item; the dispatcher fix does not waive them.

The focused producer has no public production caller and explicitly refuses structured jobs. Its old component tests must be ported to the ordinary typed producer with real prepared replies, preserving each safety invariant, before deleting its mechanical-question/unsupported-lifetime/diagnostic-English helper chain. Retaining the helpers indefinitely behind that refusal is not completion. The first port preserves a one-request fallback-quorum edit by submitting its typed approval change and validation in one actual consumed batch; it need not relax the original provider-count bound.

## Actual Read review predecessor acknowledgement

For the ordinary structural-review transition, `authoring-read-review-save` owns the existing project mutation lease and native progress writer. It loads actual current records, compares the shown mutation/progress bindings, and runs the local synchronous predecessor projection check on a detached clone before saving. The callback cannot return a value or an asynchronous result. No prompt/model wait is introduced under the lease. Existing Source/Resume owners remain separate.

`onReviewSignoff(after, committed, before)` receives `before` from that protected current read, never the expected input projection. It runs only after the exact committed progress/candidate/authoring binding is reloaded. A failed save or competing successor keeps the fence and never invokes continuation. The pending public Action adapter must compare this actual predecessor with its prepared structural reference, then use the corresponding acknowledged successor; it must not adopt arbitrary latest state. Native tests are evidence for this owner boundary only, not public Action route acceptance.
