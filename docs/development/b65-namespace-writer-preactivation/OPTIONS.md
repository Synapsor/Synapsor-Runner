# Namespace replacement protection: writer provisioning options

Current Main source: `packages/postgres/src/hard-limit-source.ts:53`; PG17 READ COMMITTED/origin transaction. The native guard requires a granted SHARE-or-stronger lock on `pg_catalog.pg_namespace` in the same backend and transaction. Business-table/parent locks alone do not protect schema names. Current worker guard stays in force.

| PostgreSQL option | Exact administrator grant | Additional authority / disposition |
| --- | --- | --- |
| Relation MAINTAIN (recommended; existing native fixtures use this exact grant) | `GRANT MAINTAIN ON TABLE pg_catalog.pg_namespace TO "writer_role";` | Maintenance operations and all relation lock modes on this one system catalog. No INSERT/UPDATE/DELETE grant; namespace DDL can wait while transactions hold the lock. Use a dedicated writer role. |
| Existing table UPDATE | `GRANT UPDATE ON TABLE pg_catalog.pg_namespace TO "writer_role";` | Table-wide catalog UPDATE capability, beyond lock purpose; do not recommend or generate as a repair. |
| Existing table DELETE | `GRANT DELETE ON TABLE pg_catalog.pg_namespace TO "writer_role";` | Catalog-row DELETE capability, beyond lock purpose; do not recommend or generate. |
| Existing table TRUNCATE | `GRANT TRUNCATE ON TABLE pg_catalog.pg_namespace TO "writer_role";` | Table truncation privilege/all lock modes, unnecessary and dangerous; database command restrictions still apply. Do not generate. |
| Global maintenance role | `GRANT pg_maintain TO "writer_role";` | Maintenance/locking on all relations, much broader than one catalog; the least-privilege writer boundary must not be waived to admit it. |
| Already held qualifying lock | No new grant at this guard | Existing trusted Source transaction must actually hold the lock on the same backend; another connection's lock or operator assertion is insufficient. A preflight connection's temporary lock is not evidence that future worker sessions will hold it. |

The privilege-to-lock mapping is documented in [PostgreSQL17 LOCK](https://www.postgresql.org/docs/17/sql-lock.html). The MAINTAIN operation set is documented in [PG17 privileges](https://www.postgresql.org/docs/17/ddl-priv.html); global role breadth in [PG17 predefined roles](https://www.postgresql.org/docs/17/predefined-roles.html). Each SQL example uses an exact quoted role, no PUBLIC/grant option/default privilege change. Catalog modification grants are listed to explain existing native alternatives, not permission to apply them.

No equivalent no-extra-privilege PostgreSQL replacement guard is currently established. ACCESS SHARE, parent row locks, advisory locks or an operator promise cannot be reported as protecting against arbitrary concurrent namespace replacement. A separately reviewed owner function could delegate a narrowly scoped lock (EXECUTE grant only), but that creates a Source capability/authority boundary and is not the present fix. Its support would require independent inspection and concurrency proof; no helper is provisioned here.

MySQL8.4 has transaction-lifetime metadata locks on used tables without an extra catalog-lock grant ([metadata locking](https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html)). Ordinary scoped table SELECT acquires this metadata protection; locking reads additionally require SELECT plus UPDATE/DELETE/LOCK TABLES ([locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)). The accepted parent-row purpose grant is an exact column grant, for example ``GRANT UPDATE (`budget_id`) ON `app`.`budgets` TO 'writer'@'localhost';``, alongside the exact required SELECT columns. Global LOCK TABLES is unnecessary. This does not by itself establish the complete hard-invariant Source inspection/effect inventory. Current MySQL adapter has no `assertHardLimitSource` implementation, so no additional MySQL grant can make this native hard-limit contract supported today. Setup must report/refuse that capability gap rather than imply a grant repairs it. No MySQL engine expansion is included.
