## Minimal assistance adapter proposal (not implemented)

Use the existing strict submission tool's mutually exclusive typed assistance branches, each carrying an existing scope `requirement_id` and exact host-bound scope/target identity. Presentation text is not routing authority. No new record store, language classifier, source query, model tool, or capability is introduced. Main/reviewer must agree the canonical schema and existing checkpoint representation before implementation.

**Observed values:** allow one `value_request` with an exact catalog resource/field and current requirement binding. Reuse `parseReadValueRequest`, `validateReadValueContextDecision`, the current `valueRequestHandler` and its existing one-request counter. The public handler `promptReadBoundaryValueContext` never queries rows: it offers separately confirmed manually supplied values or intentional `without_values`, with default-No egress, secret screening and existing size limits. Blank/Escape/EOF remains pending. Persist the actual consumed question and exact typed decision through the existing assistance checkpoint before continuation; replay neither question nor decision. Re-check binding before/after the unlocked wait. A raw meaning answer is never substituted for this disclosure consent. Run `approvedValueContextIssue` before accepting the typed mapping so approved field/value restrictions cannot be bypassed by the typed early-return path. Preserve all existing scope, compiler and allowance checks.

**Structural relationships:** a typed request names the current requirement and inspected exact root/path identity. Reuse `relationshipReviewHandler`, `validateReadWorkloadRelationshipPreparation`, disabled candidate save, current structural-review record and existing three-review limit. Review approves only the inspected structural path; it does not establish business meaning, selection, field disclosure, or whole-resource permission. Recompute catalog/currentness after the acknowledged exact path change and remap through the same finite scope validator. Retain the existing pending/decided/history checkpoint machinery with explicit typed binding; do not relax the new unsupported-legacy-shape fence wholesale.

Required independent variants before either adapter is accepted: wrong/stale requirement and target; changed Source during wait; cancel vs intentional decline; save/ack failure; cold dispatch retains the exact decision/counter; repeated request after the limit; values on another field or omitted approved constraint; relationship with another path/private key or same-name root; no automatic query/egress/authority on any assistance response.

## Remaining principal-scope language dependency (read-only audit)

`boundary-commands.ts` currently uses `jobRequestsPrincipalIsolation` both to start ordinary principal review and to derive `principalScopedRootResources`; `readWorkloadCatalog` marks the other roots relationship-only. Removing only the regex gate would broaden presentation. Current typed requirements have exact resources/operations but no explicit subject-scope applicability, and `intended_use` must not become another English classifier. Proposed ownership: canonical typed scope carries a proposed session-principal / existing reviewed resource-scope / unresolved subject requirement, without any model-supplied identity. Main resolves it through existing protected principal-scope options/reviews and host-injected context, preserving ordinary compiler scope and separate review; unresolved intent stays pending. This requires schema/reviewer agreement before implementation, and is not covered by field or relationship identity alone. No boundary product edit was made by this lane.
