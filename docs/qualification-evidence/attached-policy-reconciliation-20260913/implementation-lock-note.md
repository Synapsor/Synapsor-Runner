# Review reconciliation ordering and limits

Source evidence and pending-work records reuse the existing project authority mutex, policy-source session and resume CAS. Model calls and operator choices remain outside the lock. A coverage result stages its new source-session record, checks the current saved resume and draft bindings, and compares the saved source digest before its atomic file replacement. Only then does the in-memory review become current. Reconciliation records the exact old instruction, source, report and draft digests; it compares the reviewed source state again under the same lock and uses the existing resume CAS before clearing the pending field. Explicit nested permits avoid reacquiring the same SQLite writer lock. The outer lock has the existing five-second bounded wait; no new unbounded wait or lock timeout was added.

A crash between coverage persistence and reconciliation leaves the instruction pending. A failed or competing reconciliation must not report completion or overwrite newer work. History is preserved in the existing resume record, including exact legacy instructions and whether the operator or current coverage confirmed routing. Legacy prefix recognition only offers a review: it never proves origin or authorizes automatic deletion. Genuine owner edits and differing baselines retain their existing exact edit review. The bounded history limit is 16; exhaustion refuses a save rather than discarding older records. Completion cleanup retains this audit history.

These are cooperating local authoring processes and a trusted filesystem with working SQLite locks. All cooperating authoring processes must use the correction; mixed-version writers and multi-host guarantees are not established. Runtime admission/publication ordering, clocks, accounting, source effects and receipts are unchanged. Source readback remains a per-execution external observation, unverified in authoring. A saved enabled operator execution policy proves only that exact configuration record, not a fresh writer, worker, receipt-mode or independent-readback check.
