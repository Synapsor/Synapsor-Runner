## Actual evaluator, unchanged

`sqlite-proposal-methods.ts` human approval INSERT omits `action_boundary_name`; automatic policy INSERT supplies it. `evaluateActionBoundaryApprovalLimits` selects `a.action_boundary_name = ? AND a.status = 'approved'` and joins proposals. Thus human approvals (NULL boundary) are excluded. Boundary revision digest, approval class, diagnostic limit ID, proposal state and execution success are not filters. Committed approvals continue to consume allowance even if execution is blocked, until the inclusive window expires; no refund is introduced.

Time is `now-window_seconds <= approval.created_at <= now`. Explicit capability filters compare `COALESCE(proposal.capability, proposal.action)`; capability scope defaults to the candidate outcome. Boundary/tenant absence supplies no outcome restriction. Tenant, principal and object restrictions are added only for their configured scopes, using the trusted proposal context. PostgreSQL control-store admission uses the same evaluator via its serialized SQLite representation. Accounting clocks and locking are unchanged.

`counting-before-exit.json` records exit **0** for the first normal evaluator diagnostic, before product changes. Its human control used an unsupported timestamp option and is not counted as a within-window human control. Type checking exposed this setup error; it was corrected with the existing test clock and an exact stored timestamp assertion. `review-focused09/counting-contract.json` contains the corrected fourteen decisions and durable approvals, through the byte-identical admission evaluator (`counting-query-unchanged.json`): same automatic history consumes both predicates; another outcome consumes only the unfiltered predicate; human history, another boundary/tenant and expired history consume neither; the exact inclusive start still consumes both. Different principals in one tenant share the count. These are synthetic diagnostics, not observed tournament effects.
