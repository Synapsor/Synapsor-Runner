# Separate protected/named Read assessment

`app.explore_data` uses `projectScopedExploreResultForModel` in `apps/runner/src/scoped-explore.ts`, which checks the reviewed analysis grants and already chooses a unique token per selected private cell. The manual correction supplies the missing restriction before separate activation.

`packages/mcp-server/src/tool-catalog.ts` instead calls `projectProtectedReadResultForModel` for named capability results. Its `tokenFor` does reuse tokens for equal values. The owned local probe records this behavior (no source database or provider). This surface has only `model_withheld_fields`, with no `none`/`preserve_reviewed` distinction. Existing named raw-withheld analytics intentionally retain within-response comparison; see `docs/aggregate-reads.md`. Globally changing `tokenFor` would silently reinterpret those reviewed contracts. No named-read runtime, Spec, DSL, or active authority was changed in this patch.

**Remaining limitation:** `protect-query.ts:emitProtectedQueryDsl` emits `MODEL WITHHELD` without the source field's analysis intent. Exporting a private row selection to a separately activated named capability therefore cannot establish the same per-cell unlinkability guarantee. A future change would need to carry an explicit reviewed distinction through that compatibility contract and apply it in `tokenFor`, preserving old contract behavior. This is not a guarantee for the legacy named surface, nor a claim that tokenFor already hides equality. The current manual four-tool Explore route does not pass through it.
