## Cause and smallest shared correction

`createSemanticActionRuntime` supplied `claimed.claimed_at` to
`approveProposalByPolicy` after awaiting source facts. `evaluateActionBoundaryApprovalLimits`
queries committed automatic approvals using the inclusive interval
`[admission time - window_seconds, admission time]`. In the failing interleaving,
the later request committed first, with a timestamp later than the resumed
request's old claim time. The upper bound excluded that already committed decision.

Transactions were already present. SQLite runs all applicable limit checks,
approval insertion, proposal-state update and audit events inside `BEGIN IMMEDIATE`.
The PostgreSQL control-store facade acquires its existing schema-wide advisory
transaction lock, materializes current durable ledger entries, invokes this same
SQLite primitive, persists the result and commits before returning success.

Only two product functions change:

- The semantic caller stops passing evidence time as approval time. Evidence and
  proposal creation keep their original trusted claim timestamp.
- The store chooses its default trusted admission timestamp inside the existing
  transaction, after acquiring the writer lock. Previously even its default clock
  was read before a potentially blocking `BEGIN IMMEDIATE`.

Both allowances are evaluated against one current snapshot before one durable
automatic decision is inserted. Failure of either allowance inserts neither
approval nor partial consumption; normal exhaustion retains `pending_review`.
No model-facing argument, policy value, selector, scope binding, eligibility rule,
schema, migration, reservation system or source-effect behavior changes. The
explicit store `now` option remains an internal trusted test override.

## Reachability and operational consequences

An ordinary connected client can trigger the defective ordering with valid
concurrent `app.request_change` calls for distinct subjects obtained through the
four public tools. No extra model-facing approval tool, forged scope, modified
query result or test-only authority is required. The saved driver forced a legal
out-of-order fact-read completion to make the race reproducible. Reachability is
supported by that public call path and code analysis; natural occurrence rate was
not measured.

A single MCP process can be affected; multiple processes sharing the same control
ledger can also encounter it. SQLite shared-file and PostgreSQL shared-schema
control-store paths use the affected common primitive. A PostgreSQL or MySQL
business source does not determine the control-store backend. Sequential requests
that finish admission before the next claim do not exhibit this ordering;
human-only/read-only configurations do not create automatic decisions. Separate
control ledgers do not share one allowance and are not a global cap configuration.
Supported SQLite processes still require their normal filesystem/lease rules;
this test does not authorize unsupported multi-host file sharing. Across hosts,
trusted clocks must remain correctly synchronized as before; backward clock jumps
or arbitrary clock skew were not repaired or qualified here.

A committed automatic approval consumes allowance for the rest of its applicable
rolling window even if its worker is blocked, permanently stuck, never starts or
never produces a receipt. The event remains in durable history after the window
expires. Operationally, stuck work reduces later automatic capacity until expiry,
although it may have produced no business effect. There is no refund/requeue
feature in this change. Queue publication remains a separate recoverable operation:
a lost response after approval cannot erase that decision, and repeating the same
request after restart reuses it and idempotently enqueues at most one queue item.
An aborted approval insert rolls back; database errors remain errors, not successful
human-review responses. The test does not simulate an uncertain PostgreSQL COMMIT
or prove universal exactly-once execution.

Existing stores require no migration. Deployment must update all cooperating
admission processes; leaving an old caller running retains the old timestamp bug.
Prior over-admitted decisions are preserved as historical failures, not refunded
or retroactively validated. The saved failed queue has not been executed.
